# 负载估算与容量规划

## 用户数转请求率

200名注册同学是用户规模，不是200路同时生成。必须观察日活、每天请求次数、午饭/下课峰值、平均每个请求模型调用次数和请求长度。以下仅为可替换的计划假设，不是已收集流量或测试报告。

| 假设项 | 示例 |
|---|---|
| 总用户 | <=200 |
| 日活用户 | 200×20%=40 |
| 每活跃用户每日请求 | 4 |
| 日请求 | 160 |
| 24小时平均到达率 | 160/86400≈0.00185请求/秒 |
| 峰值到达率假设 | 20请求/分钟≈0.333请求/秒 |
| 平均端到端处理时间假设 | 30秒 |
| 按Little定律稳态在途量 | L≈λW≈10 |

以上峰值与30秒未经实测。4个vLLM active sequences是推理调度上限起点，不等于10个API请求能同时立即完成；后端没有显式容量限流/排队预算，模型内部会排队或请求超时。如果实际20次/分钟且处理30秒，需实测排队并决定减少工作量、提高吞吐或新增入口限流，不能只承诺“200人够用”。

一个chat可能有多轮模型调用，模型请求率约为chat到达率×平均模型调用次数；同时统计输入/输出token分布，否则请求/秒无法横比模型容量。

## 显存

仅按32×10^9主权重、4位估算：32e9×4/8=16e9字节≈14.9GiB，理想均匀TP2约7.45GiB/卡。这是简化下界，不是实际模型显存。真实参数总量、AWQ辅助参数、未量化张量、CUDA图、通信缓冲、激活与KV都额外占用。

一般KV估算式：2×层数×KV头数×每头维度×每元素字节×总缓存token数。TP分片方式、block管理和实现决定每卡占用，应读实际config和vLLM日志确认；不要用query head数量替代KV head数量。模型dtype half不代表KV必定按4位存。

两张4090不是一个连续48GiB设备；每张都要容纳各自分片与运行时。8192上下文、4序列、0.90显存利用率仅为模板起点，保留BGE在CPU避免GPU竞争。目标机还要预留系统RAM与磁盘给权重加载、Chroma和嵌入，不能由GPU型号推断这些资源已经足够。

## Redis与SQL

会话缓存TTL=259200秒。估算缓存字节应为活跃会话数×实测快照平均大小×Redis对象开销，再留余量；不简单按200个键推断占用，因为每人多会话且历史未分页。示例若600会话×50KiB约29.3MiB只是净JSON量，不能当实测内存。

SQL保留完整消息和偏好，不受Redis3天TTL清理。应测量每轮消息长度与每日增量，制定独立保留周期；当前没有自动归档/删除任务。RAG启动全量编码，资料规模增加时启动时间与RAM需单独测。

## 选型与调整证据

学院小规模场景先保留单worker、本地工具、明确结果渲染和可失效缓存。真实压测按 [计划](load_test_plan.md)逐级测试1、2、4、8、16并发，记录队列、时延、显存与错误。这里没有真实双卡报告，也不存在已根据真实报告调整出的最终容量。
